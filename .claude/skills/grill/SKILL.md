# 动手前的需求盘问循环

核心是把模糊需求中的决策分支逐项收敛，而不是拿着猜测开干。盘问只服务于真正会改变实现或验收方式的未定项。

## 何时启用

- 改配置表结构：新增/删除字段、改字段含义或 ID 规则。
- 改数值规则：概率、奖励、难度、小游戏参数等会连锁影响其他系统的调整。
- 改存档格式、数据真实源、架构职责或数据流向。
- 跨多个模块，或需求含“等等/类似的/顺便”等边界不清的措辞。
- 用户显式输入 `/grill`，要求审查当前方案。

明确、单点、低风险的改动（一句文案、一个注释、清晰的单文件修复）不要盘问，直接执行。

## 盘问循环

1. **列未定项**：明确边界、默认值、异常分支、旧数据兼容、影响模块和验收方式。
2. **逐组提问**：优先使用 `AskUserQuestion`，问题与选项使用中文；推荐项标为“(推荐)”。一次只问一组相关问题，每个问题都必须能改变后续实现。
3. **更新清单**：根据回答删除已解决项；回答引出新分支时继续收敛。
4. **复述方案**：所有决策项解决后，简要复述要改的文件/表、取值、兼容策略、影响范围和验收方式。
5. **进入计划或实现**：需要代码改动时遵循计划审批流程；实现中冒出新的关键分支则回到第 1 步。

## 必须覆盖的适用维度

- **数据真实源**：修改 Excel 源表、SQLite、JSON 派生数据还是代码常量？派生文件是否需要重新导出？
- **取值与边界**：范围、默认值、上下限、空值/0/负数的行为。
- **兼容性**：旧存档、已有配置、数据库表和序列化字段是否受影响，是否需要迁移。
- **连锁影响**：哪些 Bean、Service、Manager、Handler、UI、MsgEnum 事件或枚举引用它。
- **范围边界**：本次明确不做什么，避免“顺便”扩大改动。
- **验收**：怎样算正确，能否通过静态检查、Unity 场景、指定数据或复现步骤验证。

## 避免

- 未定项仍存在就开写。
- 询问对实现没有影响的问题。
- 一次抛出过多无关问题。
- 跳过方案复述和计划审批。
- 把用户的回答扩张成未授权的新需求。

## 与现有规则衔接

- Excel 操作遵循 `excel-io` 和项目现有导出流程。
- 架构或大型系统改造可先由 `il-system-architect` 做只读分析。
- 需要长期保留的约定按项目记忆规范记录；路径一律使用相对地址。
