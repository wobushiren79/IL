# 调试纪律

先理解再动手。IL 的逻辑常跨 Service、Manager、Handler、Bean、UI 和全局事件多层，症状出现的位置不一定是根因。

## 六步流程

### 1. 复现（Reproduce）

- 确认稳定触发方式：所在场景、操作顺序、相关配置/存档、输入数据和完整异常堆栈。
- 区分必现、偶发与仅特定数据出现；记录实际结果和预期结果。
- 无法复现时先补齐复现步骤、日志或最小测试数据，不凭描述直接扫射式修改。

### 2. 最小化（Minimize）

- 去掉无关 UI、配置项、事件和业务流程，找到让症状出现或消失的关键变量。
- 优先缩小到单个 Handler/Manager 调用、单条配置、单个存档字段或一次事件发布。
- 使用现有只读工具辅助定位：场景挂载用 `il-scene-init-check`，事件链用 `il-event-flow-trace`，SQLite 结构用 `il-sqlite-schema-check`。

### 3. 假设（Hypothesize）

- 写下具体、可证伪的根因假设，并列出少量候选，按证据和可能性排序。
- 明确每个假设对应的验证信号，例如某字段在调用前已为 null、同一事件被重复订阅或 SQLite 列名不一致。

### 4. 插桩（Instrument）

- 用断点、Unity Console 或关键中间值日志验证/推翻假设，不靠直接改代码碰运气。
- 重点检查 Bean 取值、Service 读写、Manager 状态、Handler 初始化、MsgEnum 事件发布/订阅和 UI 生命周期。
- 临时插桩只保留在排障期间，修复后清理；不要改存档或正式配置来制造“通过”。

### 5. 修复（Fix）

- 证据确认根因后再改，修根因而非在症状点随意加 `if` 绕过。
- 控制最小改动范围，不顺手重构无关模块。
- 复杂或跨模块定位可委派 `il-bug-hunter` 做只读分析；最终修改仍由主流程按确认范围执行。
- 同步更新受影响的 XML 注释与相关 Agent/Skill 文档，不保留已经失效的说明。

### 6. 测试（Test）

- 回到原始复现路径，确认症状消失。
- 验证相邻分支和回归场景，尤其是事件重复注册、场景切换、存档兼容、空数据和 UI 重复打开。
- 可执行现有静态检查或 Unity 验证；无法实跑时明确说明未验证项，不把“可能修好”写成“已修复”。

## 禁止的反模式

- 跳过复现和证据直接改。
- 一次修改多个无关文件看哪个有效。
- 只掩盖症状，不处理数据源或生命周期根因。
- 只验证原症状，不检查回归。
- 删除日志、配置或存档来让错误消失。

## 输出

排查结束时报告：**根因位置与调用链**、**为什么会错**、**实际改动**、**验证方式与结果**、**仍未验证的风险**。
